## 1. virtual_plc.py —— 虚拟 PLC 从站（Modbus TCP Server，502 端口）

### 1.1 用途

没有真实 PLC 硬件时，在本机模拟一台 Modbus TCP 从站，供 api_server（8080）读写保持寄存器，
整套联调（下发工单、工位流转、HMI 指示灯、HR0 反向控制）都能跑通。

### 1.2 代码逐段讲解（全文件仅 40 行）

```python
from pymodbus.server import StartTcpServer
from pymodbus.datastore import ModbusSequentialDataBlock, ModbusDeviceContext, ModbusServerContext
```

导入 pymodbus 的服务端与数据区组件。

```python
store = ModbusDeviceContext(hr=ModbusSequentialDataBlock(0, [0] * 100))
context = ModbusServerContext(devices=store, single=True)
```

- 建一块从地址 0 开始、连续 100 个的**保持寄存器（HR）**数据区，初值全 0；
- `single=True` 表示只有一个从站单元，主站连接时不需要区分 unit id（从站号）。

启动前在控制台打印寄存器映射表（HR0 状态 / HR1 工位 / HR2 产量 / HR4 合格 / HR5 不良 /
HR6 机械臂），方便联调对照。

```python
StartTcpServer(context=context, address=("0.0.0.0", 502))
```

阻塞式启动 Modbus TCP 标准端口 502，监听所有网卡，进程不退出服务就一直在。
寄存器值由主站（api_server）写入后保留在内存中，进程重启即清零——这也是
api_server 轮询首次读到 HR0 时要「只建立基线不动作」的原因。

### 1.3 为什么必须是独立进程

`StartTcpServer` 是阻塞死循环，不能 import 进 Flask 进程里跑；独立进程还有隔离好处：
从站崩溃不会拖垮网站服务，重启 api_server 时管理器会自动把它重新拉起。

## 2. virtual_plc_manager.py —— 虚拟 PLC 子进程管理器

### 2.1 职责

被 api_server 调用，根据当前配置的 PLC IP 自动决定虚拟 PLC 子进程的启停。
模块内全局变量 `_process` 记住当前子进程对象（None 表示没在跑）。

### 2.2 函数逐个讲解

- `_is_loopback(ip)`：判断目标 IP 是否属于「本机仿真」——
  127.0.0.1 / localhost / ::1 / 0.0.0.0 都算（统一小写、去空格）。
- `start_virtual_plc()`：
  - 已在运行（poll() 返回 None）直接返回 True；
  - 用 `subprocess.Popen([sys.executable, virtual_plc.py])` 启动，工作目录设为脚本目录，
    stdout/stderr 丢到 DEVNULL（不弹黑窗、不刷屏），Windows 下加 `CREATE_NO_WINDOW` 标志；
  - sleep 0.8 秒给从站启动时间，再 poll 一次：活着就打印 PID 返回 True；
    立即退出通常意味着 502 端口被占用，返回 False；其他异常只告警不抛出。
- `stop_virtual_plc()`：先 `terminate()` 温和终止并等待最多 3 秒，超时再 `kill()` 强杀，
  最后把 `_process` 复位回 None。
- `ensure_virtual_plc_for_ip(ip)`：唯一的对外策略入口，返回 `(是否该用虚拟PLC, 状态是否变化)`：

| 目标 IP | 子进程当前 | 动作 |
|---|---|---|
| 本机回环 | 没跑 | start_virtual_plc() |
| 真实设备 IP | 在跑 | stop_virtual_plc() |
| 其他组合 | — | 什么都不做 |

两个典型调用点：api_server 启动时按 config.json 的 IP 执行一次；
HMI/设置页调 `/api/plc/config` 改 IP 时再执行一次——填 127.0.0.1 自动有虚拟 PLC，
填真实 IP 自动停虚拟 PLC，无需手工开命令行。

## 3. db_server.py —— 数据库服务（6060 端口，唯一直接连库的进程）

这是本次架构调整新增的服务：把原先散在 common.py 里的数据库驱动、连接、SQL 方言兼容和快照同步，
全部收进一个**只干数据库这一件事**的独立进程。

### 3.1 为什么单独拆一个服务

- 整个项目只有它 `import pymysql` / `import sqlite3`，也只有它持有数据库连接；
  接口服务（8080）、页面服务（6021）连数据库驱动都不再需要；
- 端口由 common.py 的 `DB_SERVICE_PORT` 决定：读 config.json 的 `db_service.port`，默认 **6060**；
  调用方目标地址默认 `127.0.0.1`（`db_service.host`）；
- 对上游只暴露一组 JSON 接口：SQL 用 HTTP 传进来，结果行用 HTTP 传回去。

### 3.2 对外接口一览（请求与响应都是 JSON）

| 方法 路径 | 作用 | 关键参数 / 返回 |
|---|---|---|
| GET /db/health | 探活 | 返回 ok / engine / host / database / port / sessions |
| POST /db/init | 建库、建表、补列、写入基础数据（幂等） | 返回实际生效的 engine |
| POST /db/session/open | 开启事务会话 | 返回 session_id |
| POST /db/session/execute | 在会话中执行一条 SQL | 入参 session_id/sql/args；返回 columns/rows/rowcount/wrote |
| POST /db/session/commit | 提交事务 | 返回 wrote（本次会话是否写过库） |
| POST /db/session/rollback | 回滚事务 | — |
| POST /db/session/close | 关闭会话、释放连接 | — |

所有接口都套了统一异常处理：出错返回 `{"ok": false, "error": "..."}`，不会往外抛 HTML 错误页。

### 3.3 会话模型

- `open_session()`：新建连接与游标（`CompatCursor`）登记进 `_sessions`，返回 `session_id`；
- `execute_on_session()`：在会话锁内执行 SQL，一次性把结果全部取回；行里的值**在服务端就转成可 JSON 类型**
  （`json_value()`：Decimal→int、datetime→"YYYY-MM-DD HH:MM:SS"、date→"YYYY-MM-DD"、bytes→utf-8 文本），
  所以 HTTP 传输不会遇到无法序列化的对象；
- `commit_session()`：提交事务，**若本次会话有写操作**则顺带调用 `sync_to_project_files()` 生成快照；
- `rollback_session()` / `close_session()`：回滚事务、关游标关连接（会话不存在时视为已关闭，不报错）；
- 后台线程 `_reap_idle_sessions()` 每 30 秒扫一次，把**空闲超过 300 秒的会话**强制回收，
  兜底应对客户端进程崩溃导致的连接泄漏。

### 3.4 引擎探测与自动降级

`detect_engine()` 把结果写进本进程的全局 `ENGINE`（"mysql" / "sqlite"）：

1. config.json 的 `database.type` 是 `sqlite` → 直接用 `data/mes.db`；
2. 是 `mysql` 或默认的 `auto` → 先试连 MySQL（**不带库名**、connect_timeout=3 秒），连上就用 MySQL；
3. 连不上 → **自动降级 SQLite** 并打印原因，所以教学机没装 MySQL 也能一键跑起来。

`get_db_connection()` 按当前引擎建连接：SQLite 用 `check_same_thread=False`（后台线程也要用）、
`row_factory=sqlite3.Row`（按列名取值）、timeout=10；MySQL 返回 pymysql 连接。
建表语句统一按 MySQL 语法写，到 SQLite 由 `prepare_sql()` 改写方言，业务层不需要写两套 SQL。

### 3.5 初始化、快照与换库回填

- `init_database()`（原 common.py 里 init_db 的实现，函数名改掉了）：探测引擎 → 建库 → 建 6 张表
  → `ensure_column()` 逐列补字段 → 写入内置管理员、PRODUCTS、STATION_DEFS 基础数据
  → 检测库签名是否变化、必要时回填 → 导出一次快照并写新签名；整个过程幂等；
- `sync_to_project_files()`：把 6 张业务表整表导出成 `data/sync/<table>.json`
  （先写 `.tmp` 再 `os.replace` 原子替换），触发时机是「会话提交且本次有写操作」，即 3.3 里的 commit；
- `sync_from_project_files()`：启动时若发现 `data/.last_db` 记录的库签名（host:database）与当前不同
  （说明换库了），就把 JSON 用 `REPLACE INTO` 回填进新库，保证换库不丢教学数据。

### 3.6 启动

```
python backend/db_server.py     # 监听 6060（start.bat 会第一个拉起它）
```

启动时先起空闲回收线程，再 `app.run(port=DB_SERVICE_PORT, threaded=True)`；
api_server 启动时若发现它没在跑，也会以子进程方式把它拉起来（见 12 号文档）。

## 4. tests/check_ui.py —— Playwright 前端 UI 冒烟测试

### 4.1 定位

只读的端到端页面巡检脚本：用 Playwright 驱动本机 Microsoft Edge（channel="msedge"），
真实打开 6021 上的每个页面，验证能渲染、不横向溢出、无 JS 报错。不发任何 PLC 控制指令。

### 4.2 测试常量

- `PAGE_PORT = 6021`：页面服务；`API_BASE = http://127.0.0.1:8080`：接口服务；
- `ROUTES`：10 个受保护页面路由清单（首页、工单、在制、虚拟、配方、品质、异常、设置、HMI、用户）。

### 4.3 main() 流程

1. 启动 chromium（Edge）与一个全新浏览器上下文；监听 `pageerror` 事件收集所有 JS 异常；
2. **先用 API 登录**：直接 POST 8080 的 `/api/login`（账号取环境变量，默认 admin/ADMIN），
   断言响应 200——Cookie 存进上下文，之后页面请求都带登录态；
3. 三种视口宽度 1440（桌面）、1024（平板）、390（手机）逐页访问：
   - 断言 HTTP 200；
   - 断言 console.css 恰好加载 1 个、`.app-shell` 主框架存在 1 个；
   - 用 `document.documentElement.scrollWidth > innerWidth` 判断是否出现横向滚动条溢出；
   - 在 /hmi 页额外等工位指示灯渲染，并断言 7 个工位标题高度都 < 48px（防止窄屏标题挤压换行）；
4. 1440 和 390 宽度下对 HMI、配方、首页整页截图存到系统临时目录；
5. 工单页交互：点「待生产」筛选按钮断言加上 active 类；搜索框填不存在的关键字，
   断言可见工单行数为 0；
6. 在制页交互：依次点击 plc/robot/trace/flow 四个选项卡，断言对应面板可见；
7. 清 Cookie 后访问 /login、/register，确认公开页在 390 宽度下也不溢出；
8. 最后输出 JSON 结果（检查项数、溢出清单、JS 错误清单），
   并用 assert 保证「零横向溢出、零 JS 错误」，否则脚本以失败退出，可接入 CI。

### 4.4 与系统代码的对应关系

这个脚本实际上是「30 号附录对应表」的自动验证版：路由清单对应 server.py 的页面路由，
`.app-shell`/console.css 对应 base.html 的母版结构，筛选按钮/选项卡对应 orders.js、line.js
里的事件绑定，登录走 api_server.py 的 /api/login。
